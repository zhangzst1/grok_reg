# 验证码字符类型兼容设计

## 目标

让 `VerificationCodeFetcher.extract_code()` 能从邮件内容中提取所有符合 `XXX-XXX` 格式的 ASCII 验证码，包括纯字母、纯数字以及字母数字混合形式。

## 已确认根因

现有 `_CODE_PATTERN` 已允许每一位使用 ASCII 字母或数字，因此能够匹配 `JFH-KOB`、`123-456` 和 `8UP-77Z`。但 `extract_code()` 在匹配后额外要求候选值同时包含字母和数字，导致纯字母与纯数字验证码被丢弃。

## 行为设计

删除“必须同时包含字母和数字”的候选过滤条件。保留现有格式、边界、上下文评分和歧义处理逻辑：

- 验证码仍必须是三位 ASCII 字母或数字、一个连字符、再三位 ASCII 字母或数字。
- 匹配不能嵌入更长的字母、数字、下划线或连字符标识符中。
- 有验证码上下文的候选优先于邮件头或无标签候选。
- 多个无上下文候选仍视为歧义并返回 `None`。
- 返回值保留连字符，字母统一转换为大写。

示例：

- `Verification code: JFH-KOB` 返回 `JFH-KOB`。
- `Code: 123-456` 返回 `123-456`。
- `Your xAI verification code is 8UP-77Z` 返回 `8UP-77Z`。

## 实现范围

只修改 `utils/verification_code.py` 中的候选过滤逻辑，不重写正则、不调整邮件 API、重试或代理行为，也不改动调用方接口。

## 测试设计

在 `tests/test_verification_code.py` 中增加或调整回归测试，覆盖：

1. 带验证码标签的纯字母代码可以提取。
2. 带验证码标签的纯数字代码可以提取。
3. 现有字母数字混合代码继续可以提取。
4. 小写纯字母代码继续统一为大写。
5. 现有非 ASCII、嵌入标识符、多候选歧义和上下文优先级测试继续通过。

完成后运行完整 `unittest` 测试套件与 `mise run check`。

## 风险控制

允许纯字母和纯数字会增加普通 `XXX-XXX` 文本成为候选的可能性。现有上下文评分、主题行识别、边界检查和多候选歧义拒绝机制保持不变，用于限制误提取风险。本次不扩大格式长度或允许额外符号。
